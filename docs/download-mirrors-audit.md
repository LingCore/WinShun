# 下载镜像检查与补齐（2026-10-30）

本次检查真实资源下载入口并补齐镜像回退，没有提交、推送或发布。原有 Win顺进程保持运行，自动验证使用临时配置、临时注册表和独立程序目录，没有运行下载到的安装程序。

## 共用机制

默认镜像只维护一份：`resources/downloads/github-mirrors.txt`。

```text
https://gh-proxy.com/
https://ghfast.top/
```

`cmake/Download.cmake` 从该文件生成客户端使用的 `GitHubMirrors.h`，构建下载也直接使用同一配置。修改镜像后需要重新配置和构建程序。

`src/core/Download.*` 提供源选择和可注入网络传输的下载流程。`plugin::gallery` 复用这些类型和函数，OCR 也使用同一套回退。主程序更新继续流式写文件和计算哈希，没有改成把整个安装包读进内存；只共用源选择和慢源规则。

- 公开、无查询参数和凭据的 GitHub Release / Raw 文件默认先走两个镜像，再走原站。已有镜像地址不会重复套前缀，其他网站、本地文件、API、带令牌 / 凭据的链接保持原地址。
- 更新服务显式给出的镜像保留其相对顺序，去掉重复地址，原站放到最后。
- HTTP 成功但内容未通过业务校验时，继续尝试下个来源。插件按索引中的大小和 SHA256 检查；OCR 按应用内固定的文件清单检查。
- 下载超过 30 秒且平均速度低于约 16 KiB/s、后面还有其他来源时切换；最终来源仍等待正常传输结果。此实现是按顺序回退，没有并行测速或同时重复下载整份包。
- 每个请求之前检查取消。还修复了原更新下载器在失败来源之间没有检查取消的边界，避免取消后继续发起下一次请求。
- 本地 ZIP 只在本地读取。取消、校验失败不发布半份 OCR 组件；CMake 用 `.partial` 暂存，校验通过才原子替换目标，全部失败保留原文件。
- 网络继续遵守程序已有的代理设置。没有增加截图插件的联网权限。

插件索引仍使用既有 JSON 协议做结构校验，包的预期 SHA256 来自该索引；本次没有新增索引签名，不能把 JSON 格式校验描述为签名验证。当前公网检查中两个镜像的索引字节与 GitHub 原站一致。

## 发布边界

本轮没有发布新版本，也没有重新制作上轮体积对照的安装包。上轮冻结产物的体积、哈希仍见 [安装包精简验证](package-size-validation.md)，本轮的程序副本及证据独立保存。

新 OCR 组件需要随下一版应用 Release 上传，才能使用默认公网下载；当前镜像策略和真实传输已验证，不表示该尚未发布的组件已经能在线取得。源码里可以本地导入验证包，或使用已生成的离线目录。正式发布还应按 [发布流程](releasing.md) 完成其余验证及附件核对。

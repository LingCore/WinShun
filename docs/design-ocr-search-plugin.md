# 图片文字搜索插件

实现位置 `src/ocr-search-plugin`，插件 ID `winshun.ocr-search`。这是开发版功能，公开插件库分发和新版本发布不在本次实现任务中。

## 边界

宿主只增加通用 `commands[].contentSearch` 接口与结果合并，未将 OCR、文档图片解析、数据库或管理窗口放进主程序。没有安装／启用提供者时，不启动插件任务。

插件复用现有小启动器／Qt DLL 模式：小启动器只从插件目录、`WS_APP_DIR` 和系统目录加载 DLL；Qt 与公共控件跟随宿主。PDFium 也用宿主的：插件装在用户的插件文件夹，`pdfium.dll` 在 Win顺 的文件夹，`extract::loadPdfium()` 因此要连 `AddDllDirectory` 加的目录一起找（`LOAD_LIBRARY_SEARCH_USER_DIRS`）；1.0.0 只找程序旁边，装好后每个 PDF 都失败。测试 `installedWorkerReadsPdfPages` 从复制出来的插件文件夹跑工作进程。源码和字节码一起保留，避免依赖 QML 私有 C++ ABI。UI 公共组件使用同一份 Theme、TitleBar、WindowFrame 等源码。

解析、识别和预览在插件自己的工作进程中执行，继承插件作业与普通用户令牌。`processes` 权限用于允许该子进程。每轮索引复用一个工作进程及其 OCR 实例；工作进程每处理完一页／一张图（包括跳过的）报告一次进度，识别一张图时每检测完一段条带、每认完一批文字行也报告一次（`OcrOptions` 的进度回调，剪贴板和截图不传）。进度只从识别内部报告，不用定时器代报，真卡住仍会超时。单文件连续 60 秒没有进展才算超时，取消／崩溃／超时结束该进程。索引工作进程进入 Windows 后台模式（低 CPU、I/O 和内存优先级）后，立即把工作集上下限恢复成进入前的值：后台模式会顺带加 32 MB 的工作集硬上限，ONNX Runtime 推理因此不停换页（同样三个 4000 万像素的密集页面慢约 2.5 倍），Store 版 HEIF／AV1 解码器的 `CopyPixels` 也会返回 `E_OUTOFMEMORY`。父进程的遍历线程也使用后台 I/O。预览使用独立的 30 秒工作进程。父进程只接收有界 JSON；索引响应包含文字与位置，预览响应为最长边不超过 2048 像素的 JPEG（编码失败时用 PNG，10 MB 以内），不写图片缓存。

## 索引和查询

SQLite WAL，每个调用线程独立连接，查询使用只读连接。文件表记录规范路径、原路径、大小、毫秒修改时间、SHA256、模型／流程版本、遍历代数、状态及原因。页表将文件位置映射到去重图片记录，图片记录保存压缩文字与识别框。存入和查询的文字都先经 `normalized()`：NFKC、大小写折叠；繁体字按 OpenCC `TSCharacters`（Apache-2.0，原样放在 `third_party/opencc`，许可随插件包分发）折成简体，单字对单字，链式折到底；中文／日文字符旁边的空格去掉（OCR 常在中文之间、中英之间加空格，用户也常在中英之间打空格），韩文字之间照旧去掉，其他词之间的空格保留。中文单字／双字和 ASCII 三字片段继续复用 `grams` 规则；一两个字符的 ASCII 字母数字词（`a4`、`q3`、`12`）凑不成三字片段，另存为整词词元，查询、摘要和高亮都按整词匹配（前后不能紧挨字母或数字）。关系不再逐条存入普通表：`asset_terms` 使用 FTS5 contentless、`detail=none`、`columnsize=0`，仅保存压缩候选倒排表。片段键编码为十六进制词元；不额外存正文、词频和词偏移。每个查询词先筛出候选图片，再按文件交集，最后验证压缩文字；不同页仍可分别满足不同词。片段过滤只用于排除，不能代替文字核验。整个查询既没有片段也没有整词词元时（如俄文、希腊文单词）直接返回空结果，不逐个读取文字；同一查询中有片段或整词词元的词照常筛选，其余词参与文字核验。路径条件先于文字核验；页查询只准备一次、逐文件绑定；文件大小与日期条件及存在检查只对文字核验通过的行执行。

遍历使用插件自己的 `FindFirstFileExW`（基本信息、大批量读取、长路径前缀）：先按文件名扩展名筛选，不为无关文件取属性；跳过目录重解析点和文件符号链接。某个子目录无法列出或中途读取出错时，只保留该子目录下已有的记录，同一根目录的其余部分照常清理，界面提示部分目录无法读取。

本轮见过的文件只记在内存集合里，未变化的文件不写数据库；遍历完一个根目录后，按集合在单个事务中删除未见文件。失败的文件记录状态与原因，大小和修改时间不变时不再自动重试，可用“重新检查所有文件”强制重试；离线、旧格式等状态未变化时也不重复写。工作进程启动失败、OCR 组件加载失败、因缺少 DLL／入口点退出等与文件无关的问题会中止本轮并显示原因，不记为该文件失败，下一轮照常重读。PDF 页有图片对象（含表单对象内的图片）时渲染识别。没有图片的页先看文字层：去掉空白和 PDFium 自己补的字符后，有 Unicode 的字不少于 16 个、且占一半以上时，字都在文字层里，不渲染，交给内容索引；否则有映射不到 Unicode 的字形就渲染，字都正常但很少时，页面画了路径／渐变（含表单对象内）或有链接、弹出注释以外的批注才渲染（转成曲线的字、CAD 图纸、印章）。80 个随机真实 PDF（2409 页，其中 428 页没有图片）里只多渲染了 4 页转曲的图纸；读文字层每页约 3 ms。页面按长边 2600 像素、最高 200 dpi 渲染；页上最大的图片分辨率更高时按它渲染（最高 200 dpi），总像素不超过识别上限 4000 万（`PaddleOcr::kMaxPixels`，剪贴板和截图共用）。图片：照片长边最多 4096；长宽比超过 3 的长图保留原宽度，总像素不超过 4000 万。来源记录图片原始尺寸、页面点数与图片 dpi，以后能找出被缩小的图片和页面。认得差时（检测到的行留下不到六成，或平均分低于 0.75）转 180° 再认一次，多认出 1.3 倍才采用（`OcrOptions::retryUpsideDown`，只在本插件开启）。单张图片在 WIC 读出尺寸后、缩放前检查，超过 1 亿像素直接拒绝；主程序其他调用 `PictureFile` 的地方没有这个限制。GIF 只读第一帧；WebP、HEIC／HEIF、AVIF 靠 Windows 扩展解码，WIC 读不出尺寸时按扩展名提示要装的 Store 扩展。

插件窗口除未完成项外，还列出没有识别到文字的文件及原因（PDF 的字都在文字层里、文档里没有图片、识别过但没认出字）；没有字的图片多是照片，只计数，排在文档后面；最多列 200 个文件。升级后等着按新规则重读的文件不算在内（转曲的 PDF 重读后多半就有字了），读完再按结果列。

更新单文件使用事务。读取期间文件变化、取消或异常则回滚；成功后提交。相同文件内容可复制位置记录，相同图片共享识别结果。离线目录和遍历失败保留未检查记录。排除目录及移除范围在后台线程撤掉对应索引并整理，不占用界面线程。查询还会核对现有文件大小和毫秒时间，预览复核同一时间戳；高亮框按图片记录保存的宽高归一化，与预览图的缩放无关。

数据库大小通过 `max_page_count` 约束，按数据库实际 `page_size` 换算容量。删除和整理期间临时解除这一上限（FTS5 删除要先写新页），结束后恢复，因此索引写满后仍能移除目录、清空索引。回收没有页引用的图片时，若已没有任何页引用图片，用 FTS5 `delete-all` 一次清空；否则从存储的压缩文字重建完全相同的词元，逐个提交 FTS5 删除命令；删除倒排关系与图片记录处于同一事务。随后在单独事务中整理倒排段：删除量达到图片总数十分之一时 `optimize`，否则只 `merge` 有限页数；这一步失败只回滚自身，不影响已完成的删除。没有删除也没有新写入时不整理。最后循环执行增量回收直到空闲页耗尽或不再前进，最后截断 WAL。QSQLITE 对零列的 `incremental_vacuum` 不提供 `next()` 继续步进，单次执行可能只回收一页，不能把“命令成功”当成文件已经缩小。短期 WAL、共享 OCR 组件和原始文件不属于数据库页数限额；显示占用包含数据库、WAL 和 SHM。活跃读事务可能推迟 WAL 截断。

数据库 `user_version=3`。文件行记流程标识（`pipelineEngine()`，现为 `ocr-search-3`：哪些页／图要读、按多大尺寸），图片识别缓存的键是像素摘要加识别标识（`recognizerEngine()`，仍为 `ocr-search-2`：同样的像素认出同样的字）。两者分开后，流程变了的文件重新遍历，像素没变的图片直接用回已存的识别结果。`meta` 表的 `terms` 记录片段规则版本（规则号，加固定样本经 `normalized()` 和词元规则的输出、繁简对照表的摘要）；与当前构建不一致时，在单事务内从已存识别行重建文字和倒排表，不重新 OCR。只读连接遇到需要迁移或重建的数据库会拒绝打开。版本 1 的迁移在单事务内直接从已有识别文字构建倒排表，再移除旧 `grams` 表；不读取原文件，不重新 OCR，资产 ID 与高亮框保持不变。版本 2 → 3 也不读文件、不识别：只把新规则可能多认出字的文件留在旧流程标识上，下次遍历时重读，即没认出字的 PDF、因 60 秒没有进展失败的文件、因“缺少 PDF 读取组件”失败的 PDF（1.0.0 装好后找不到 pdfium.dll，见下）、按 2600 像素渲染的 PDF 页、被缩到 4096 的长图（含 Office 内嵌图），以及含有认出至少两行、平均分低于 0.75 的图片的文件；这些图片的缓存键末尾多加一个字节，下次查不中，重认时会试 180° 翻转，重认前旧结果照常可搜。其余文件改记新流程标识，不重读。`meta` 的 `recheck` 记着旧标识，界面据此显示“识别规则已更新……还剩 N 个文件”，完整遍历一轮后删除；当时不在的目录回来后照样重读，只是不再提示。容量不足等失败回滚迁移，更高版本数据库拒绝打开。迁移成功后回收旧表空闲页。研究依据、迁移与容量回归、优化前后体积见 [2026-11-02 存储验证](validation/ocr-storage-20261102/README.md)。

搜索、预览分别使用有界线程池和取消令牌，GUI 不等待旧查询／旧解码完成。返回时核对令牌和预览版本。后台进度限频，防止未改动的大目录遍历向 GUI 排队大量信号。

打开数据库、迁移和整理都在后台线程执行；插件先回应宿主初始化，打开期间的查询回复“正在打开索引”并请宿主稍后再问（`rerun`）。外部查询只在插件正在更新索引时附带 `rerun`，内容查询去抖 150 毫秒，取消通知会丢掉尚未执行的查询。启动后首轮遍历推迟 60 秒，打开插件窗口或搜索时立即开始。增强识别组件的安装状态检查从 1 秒逐步退避到 60 秒；界面字体只在界面进程加载，工作进程不加载；窗口关闭后释放预览图。

## 宿主协议

`commands[].contentSearch: true` 声明一个内容提供者。0.17.0 没有这一接口，插件包的 `minWinShun` 与 `winshun.web` 一样，构建时设为当前主程序版本。关键词查询保持原协议；内容查询的 `trigger` 为 `content`。只在 Content 或显式开启内容检索的 All 中派发；Files / Folders 不派发。关键词独占列表时不调用其他内容提供者。提供者在原生结果之后合并（Content）；在 All 里前 3 行排在前 5 个名称结果之后，其余在最后。最多 200 行，不占普通推送的 3／6 行配额；同一文件已有原生结果时去重。

`filters` 保留原有日期、大小、扩展名及目录条件，并提供 `contentEnabled`、`contentWords`、`contentPick`、`excludedExtensions`、`excludedFileNames`。关键词、目录选择、排除文件类型／名称和异步过期结果分别有测试或生产路径验证。

## 已知边界

详见 [插件说明](../src/ocr-search-plugin/package/README.md)。首版不承诺所有历史 Office/WPS 格式和所有图片编码。Office 按图片关联读取原图，不复现裁剪、遮挡和整页版式；PDF 按实际页面渲染。文件重命名复用依靠内容指纹，而不是宿主 NTFS EntryId。仅大小和修改时间均未变化的改写需要手动检查。大数据量结论必须区分真实 OCR 样本与合成索引查询基准，不能据小样本承诺比 AnyTXT 缩小固定比例。

后续改动按影响选择标识：改变哪些页／图要读、渲染或解码尺寸、图片定位语义时，递增流程标识（`kPipeline`），并在升级迁移中只把受影响的文件留在旧标识上，其余照旧；改变同一张图的识别结果（换模型、改预处理）时，递增识别标识（`kRecognizer`），所有图片都会重认；只改文字归一化或片段规则时，`terms` 摘要自动变化，从已存识别行重建，不重认。数据库结构变动同时更新 `user_version` 和迁移策略，不能覆盖较新数据库。PPT 位置按 presentation 的实际顺序解析，不把 slide 文件名编号当作页码。

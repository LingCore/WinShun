# #111：双屏拖动跳位复查

日期：2026-11-01。基线：`804f390`；修复随本记录提交，尚未发布。

## 实际环境

- 左侧屏幕：2560×1600，150%，物理坐标 `(-2560, 0)`，工作区 2560×1528。
- 右侧主屏：LG ULTRAFINE，3840×2160，150%，物理坐标 `(0, 0)`，工作区 3840×2088。
- Windows、Qt 6.12.0、MSVC Release、D3D11；没有修改系统显示配置。

## 复现、原因与修补

用户在真实双屏上往返拖动独立搜索验证窗口，确认存在明显跳动/吸附。修补前记录到四次横跨 `x=0` 时窗口横移 1140 物理像素；其中一次鼠标仅移动 8 像素，窗口却移动了整整一个窗口宽度。

生产路径为 `WindowFrame → Windows 原生移动循环 → Placement::Hook::WM_MOVING → shapeMove`。原逻辑在每次移动中，把完整窗口矩形夹进鼠标所在的单块屏幕工作区。鼠标跨过接缝时，允许的窗口位置立即从一侧切换到另一侧，导致横移一个窗口宽度。

本次把拖动约束改为所有屏幕工作区的外接边界，允许手持窗口横跨屏幕；松手后的屏幕内归位、位置保存及靠近原锚点时的平滑吸附仍使用既有流程。使用物理坐标汇总屏幕边界，避免混用不同屏幕的逻辑原点。单屏仍保留原来的外边界限制，没有新增生产定时轮询。

可迁移的规则：多屏窗口拖动不应在内部接缝处强制整窗进入鼠标所在屏幕。拖动时跟随指针与松手后的完整可见性约束应分别处理；回归至少覆盖负坐标、水平/垂直接缝及桌面外边界。

## 验证结果

- 使用相同的独立窗口再次真实往返拖动，用户确认跳动消失。
- 修补后跨缝记录中，窗口位移与指针位移一致，采样端点之差最多 2 个物理像素；不再观察到额外横移一个窗口宽度。
- `tst_placement`、`tst_displaygeometry` 两个 CTest 目标通过。新增几何回归覆盖水平/垂直接缝、负坐标、桌面外边界、超大窗口、空屏幕列表及单屏行为；100%–200% 的窗口物理尺寸由几何用例覆盖。
- 当前主程序对象以独立文件名链接成功；真实剪贴板窗口的 150% 缩放回归退出码 0，22/22 检查通过，包含原生边角缩放、尺寸保存、预览、倒序布局和焦点保持。
- 只关闭了本次创建的临时验证窗口。原先运行的 `build/release/WinShun.exe` 保持运行，没有替换该文件或改动用户配置、历史和剪贴板内容。

证据位于忽略的 `build/multimonitor-20261101/`：

- `monitors.json`、`launcher-task-before.jsonl`、`launcher-after.jsonl`、`comparison.json`。
- `MonitorProbe.cpp`、`build-probe.py`、`build-fix.log`、`ctest.log`、`candidate-link.log`。
- `clipboard-regression/clipboard-sizing.json` 和该目录中的真实窗口截图。

## 设置窗口与验证边界

设置窗口使用真实 `SettingsWindow.qml`、`SettingsEditor` 和 `WindowFrame`，也完成了双向跨屏及 Windows 贴靠/恢复检查。尚未确认原报告中短暂卡顿的原因，这项不作为本次修复完成的内容。原生移动循环可能延迟 Qt 定时器，不能把窗口内部采样间隔直接当作渲染帧时间。

独立搜索入口加载生产 `Main.qml`、`WindowFrame` 和 `Placement`，不启动普通 App、全盘索引或剪贴板监听。为使界面工具能定位窗口，仅将搜索验证窗口的 `Qt.Tool` 类型改为 `Qt.Window`，保留无边框与置顶；修补前后使用相同配置。拖动由用户实际鼠标操作完成。该证据覆盖生产窗口的原生拖动路径，不等同于普通宿主启动的完整端到端验收。

当前两块真实屏幕都是 150%；不同 DPI 的真实切换、休眠唤醒、断开显示器和 Windows 10 尚未在本轮验证。坐标记录采样间隔不均匀，结合用户复测支持“额外整窗跳位消失”，不据此作帧率或长期性能承诺。

## 设置窗口追加复测（2026-11-01）

跳位修复已提交为 `c0a90f9`。继续读取 [报告者最新回复](https://github.com/LingCore/WinShun/issues/111#issuecomment-6545324877) 中的两段录屏及诊断包：报告者使用 Windows 10 22H2（19045）、Win顺 0.16.0，主屏 1920×1080、副屏 1080×1920，两屏均为 100%、60 Hz；D3D11、背景材质关闭，DXGI 活动适配器为 NVIDIA RTX 2080。包中没有可定位设置跨屏停顿的消息耗时或渲染调用栈。因此不能直接把原报告归因于不同 DPI、材质效果或双显卡切换。

本地新增的独立设置入口对齐普通启动的 `QT_D3D_NO_VBLANK_THREAD=1`，关闭背景材质并调用生产窗口样式函数。仍使用临时配置，不启动普通 App、索引或剪贴板监听。用户实际往返拖动后确认“没有明显停顿”。

临时原生消息钩子记录到 6 次 `screenChanged`；跨屏附近的 `WM_MOVE` / 外层 `WM_WINDOWPOSCHANGED` 最长约 44.24 ms，二者是嵌套消息，不能相加。`WM_MOVING` 最长约 0.83 ms。启动阶段一次 `WM_PAINT` 约 297.70 ms，发生在拖动开始前，不能算作跨屏停顿。计时覆盖钩子以下的消息处理链，不能精确区分 Qt、驱动和 Windows 各自的耗时，也不是显示器呈现帧时间。

本次没有为设置窗口修改渲染器或增加生产轮询。结论是本机当前双屏下未复现报告者所述的明显停顿，原 Windows 10 环境仍待复测。验证窗口已关闭，原先运行的 Win顺保持运行。追加证据位于忽略的 `build/issue111-settings-20261101/`：诊断包、两段录屏、`local-settings.jsonl.native.jsonl`、`local-settings-analysis.json`；计时入口源码保存在 `build/multimonitor-20261101/MonitorProbe.cpp`。

# 复制为表格：合并单元格与表格结构验证

2026-11-26，Windows 11 Pro 26200，`build/table-ocr`（Qt 6.12.0，ONNX Runtime 1.30.0，PP-OCRv6 tiny），截图与录屏 1.1.39。用户反馈：希望截图后识别成表格，直接在 Excel 里粘贴。原有的“复制为表格”只按文字空隙分列，不认合并单元格和一格多行，密集的表格常常认不出是表格。

做法：表格结构三级依次尝试（画出来的框线 → 表格模型 SLANet_plus → 文字空隙），文字仍用自己的 OCR；剪贴板同时放 HTML（带 `rowspan`/`colspan`）和制表符文本。

## 表格截图打分

[corpus.py](corpus.py) 用无界面的 Edge 渲染 47 张带标准答案的表格截图（100%–200% 缩放）：有框线、无框线、斑马纹、只有横线、两级表头加纵向合并、一格多行、空格子、深色、仿 Excel、密集的生产报表（21×10）、40 行长表、两列的参数表；以及更接近实际框选的：选区落在外框以内、表格上有标题下有备注、格子里有带下划线的链接和彩色标签。[score.py](score.py) 逐格比对：同行同列文字相同（相似度 ≥ 0.75）算对，标准答案为空而结果有字算多出。读法与截图插件一致（`wsbench --ocr <目录> --as-capture --tables <文件> --table-model <模型>`：100%、125% 的图先放大再认字）。

| 读法 | 单元格正确 | 多出的格子 | 整张全对 |
|---|---|---|---|
| 原来：只按文字空隙（`--words-only`） | 58.8% | 139 | 31 / 47 |
| 只按框线，没有模型 | 92.6% | 83 | 40 / 47 |
| **框线 + 模型 + 文字空隙（现在）** | **99.9%** | **0** | **44 / 47** |
| 参考：RapidTable 3.0.2（同一个 SLANet_plus 模型，RapidOCR 的文字），前 34 张 | 96.2% | 16 | 20 / 34 |

- 47 张的表格结构全部正确：25 张由框线得出，22 张由模型得出。没全对的 3 张各错 1–3 个字（“已解决”认成“已解決”、“黄”认成“黃”），是文字识别本身的问题，与表格无关。
- 耗时与原来相当：每张中位数 346 ms（原来 386 ms，各跑一遍，同一批图，4 线程），最慢 1.9 s（40 行长表）。
- 8 张不是表格的截图（中英文段落、列表、代码、菜单、聊天、标题加正文、两行字）都没有被当成表格：模型对段落和代码的把握度只有 0.92–0.95（前 34 张表格都在 0.994 以上，门槛 0.98），单列的列表过不了“至少两列各有两行字”。

实测中发现并处理的：
- 模型对线条清晰的小表格也会多认一行（参考实现在同一张图上同样出错），所以有框线的表格不交给模型，按像素找线直接得出格子；模型把同一行文字拆进两行时也不采用。
- 100% 缩放下一排数字的顶端和底端很齐、间隙只有 1–3 像素，会被当成横线：线必须沿线两侧颜色各自不变。
- 表头行另有底色时，每条竖线在表头里是单独一小段，只有一行高：竖线不按长度筛，按“两端都落在横线上”筛。
- 选区落在外框以内时没有外框线：横线伸出最外侧竖线、竖线伸出最外侧横线时补上隐含的边。
- 格子里链接的下划线、彩色标签的上下边不是表格线：横线须有一段从一条竖线伸到另一条。

## 没有验证的

- 没有在正在运行的 Win顺 里真实截图并 `Ctrl+V` 粘进 Excel：会改写系统剪贴板和剪贴板历史，留给用户实测。剪贴板里的 HTML 由 Qt 的 `QMimeData::setHtml` 写成 `HTML Format`，这一步没有单独核对字节。
- WPS 表格、Word 的粘贴（本机没有 WPS）。
- 真实软件的截图只用渲染的网页表格代替：Excel 本身（带行号列标、选中框）、手机拍的纸质表格、JPEG 压缩过的图片没有测。拍照和压缩过的图没有清晰的线，会落到模型或文字空隙上。
- 超过 4000 万像素的图不走框线和模型；模型说不完的超长表格（没有输出结束标记）退回文字空隙。

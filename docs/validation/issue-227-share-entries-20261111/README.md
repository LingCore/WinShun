# 2026-11-11：#227 网络位置的条目越读越多

报告者重建索引后，条目从 1.8 亿降到约 56 万，说明此前绝大多数条目对应不到现存文件。他公开的诊断里有两个网络位置（`share-probe-missed` 的 share 0 和 1），两个本地卷都在跟随 USN 日志，条目数在同一进程里一天涨了约 90 万。

## 排查经过

- 本机索引（349 万条，一个月的开发用量）逐条对照磁盘：只有 751 条对不上，全是导出快照后当天删掉的文件；没有重名条目，没有从根走不到的条目。本地卷这条路没有问题。
- `FileIndex` 随机增、删、移、压缩、存取快照 4 万步，每一步后“从根能走到的条目数 = 未删除的条目数 = 计数”都成立。
- 网络位置的读法不同：一遍读下来，“已经没有了”的条目只是记下，等整遍读完、结果可信才删；读到一半被打断、服务器出错或者一次少了太多，就都不删。用一个内存里的假共享做随机改动、反复读，查出问题在这里。

## 原因

对照一个文件夹的列表和索引里已有的条目时，每个名字只按“名字相同（不分大小写）”找一个已有条目，先到先得：

1. 一个名字原来是文件夹、后来成了文件（或反过来），旧条目还没删时，索引里同名的有两个。下一遍读可能拿到旧的那个，发现种类不对，就再新建一个，新建的文件夹连同里面所有内容再读一遍。只要删除一直没被采信，每读一遍就多一份。
2. 列表里同时有 `A` 和 `a`（服务器区分大小写）时，先处理的 `A` 会把 `a` 的条目拿走改名，`a` 只好新建一份。
3. 同名的条目有两个时，这一遍和下一遍可能各挑一个，两个都被填满。

本地卷上“没有了”的条目当场就删，这些情况留不下重复条目，所以只有网络位置（含 WSL、WebDAV）受影响。

## 修改

`Crawler.cpp` 的 `reconcile`：先给列表里每个名字找“拼写和种类都相同”的条目，再给剩下的名字找“只是大小写变了”或“只是种类变了”的条目；两样都不同的不算同一个。有多个合适的条目时固定取最早建的那个。

## 验证

`tst_core`（Qt 6.12.0 / MSVC Release，整个测试程序 257 通过、0 失败、4 跳过）：

- `sharePassesNeverMultiply`：假共享上随机新建、删除、文件与文件夹互换、改名（含只改大小写），6 组随机数各 400 轮。每轮读两遍，第二遍不得多出条目；删除被采信的那一轮，索引必须和共享完全一致。修改前第 49 轮就多出条目（145 → 146），去掉“文件与文件夹互换”后第 88 轮仍然多出；修改后全部通过。
- `everyLiveEntryReachable`：上面说的 `FileIndex` 随机测试，留作回归。

# #181 剪贴板元数据诊断验证

日期：2026-11-02。Windows 11，Qt 6.12.0、MSVC 2022、Release 构建。

本次为 [#181](https://github.com/LingCore/WinShun/issues/181) 增加排查证据，没有确认 UU 乱码的根因，也不宣称修复该问题。没有默认排除 GameViewer、修改编码策略、拦截 UU 或改变原有剪贴板读取及重试策略。

## 实现范围

- `ClipboardWatcher::diagnosticStatus()` 提供线程安全的内存快照；导出时放入现有诊断包 `summary.json` 的 `clipboard` 字段。快照本身不访问系统剪贴板。
- 最近 16 次实际读取尝试，每次最多 64 个格式 ID；只标注代码中固定列出的已知格式名称。未知注册格式名称可能含私密数据，因此不导出其名称。
- 记录读取前、打开后及结束读取时的序列号，所有者 PID、来源 PID/程序文件名、是否使用前台程序回退，打开尝试次数及最近一次失败的错误码、占用进程，以及读取结果。
- Unicode 文本的分配字节数、UTF-16 单元数、终止符及奇数字节状态来自原有读取过程。没有额外请求正文、CF_TEXT、CF_LOCALE 数据或其他格式来做诊断。原有处理仍优先读取 CF_UNICODETEXT。
- 三种既有隐私标记继续阻止正文读取；此类诊断条目没有文本长度或格式列表。按应用排除也不读取文本。
- 不采集正文、内容哈希、完整程序路径、窗口标题；不逐次写入磁盘。重启即清空，只有用户主动导出时才写进诊断包。
- 可用格式列表包含 Windows 可合成的格式，不能据此断言源程序直接写入了哪些格式。序列号变化也不能直接视为竞态或乱码证据。

## 验证结果

`WinShun`、`tst_pinclipboard`、`tst_cliplifecycle`、`tst_diagnostics` 构建成功。完整构建输出见 [build.log](build.log)，修正原生测试后重建的输出见 [build-tests-final.log](build-tests-final.log)。构建中有原有 App.cpp 的局部变量遮蔽警告和 Qt 生成代码的不可达代码警告。

最终 CTest：3/3 通过，0 失败，15.33 秒；见 [ctest.log](ctest.log) 和 [native-tests.log](native-tests.log)。

| 验证路径 | 结果 |
| --- | --- |
| 真实 CF_UNICODETEXT 读取 | 内容完整，字节数、长度和序列号元数据正确；来源所有者为空时明确标注前台回退 |
| 正文、哈希与格式名称隐私 | JSON 中没有正文、其哈希的十六进制/Base64 表示或未知格式名称；未知格式仅有数字 ID |
| 三种隐私标记 | `ExcludeClipboardContentFromMonitorProcessing`、`Clipboard Viewer Ignore`、`CanIncludeInClipboardHistory=0` 均不产生正文捕获或长度元数据 |
| 容量和并发快照 | 超过 16 次读取后只保留最近 16 次；68 个未知格式截为 64 个并标注截断；另一线程持续读取快照通过 |
| 剪贴板被占用 | 10 次打开尝试失败后记录错误码和占用程序，释放锁后按原有定时重试捕获成功 |
| 原生延迟渲染 | Unicode 内容完整，只渲染一次；另一个声明为延迟渲染的未知格式没有被请求 |
| 诊断包导出 | 元数据上下文进入 ZIP 的 summary.json；原有文件白名单、隐私文件排除、限额及覆盖导出测试通过 |
| 生命周期与既有图片路径 | 模块关闭/重启/空写入退休测试，以及原生图片、Qt 延迟渲染和 WIC 解码回归通过 |

原生剪贴板套件共 24 项通过。该套件将子进程置于非交互窗口站和独立桌面，验证不是 WinSta0 且剪贴板为空后才执行写入；不会替换用户当前剪贴板。其余测试使用临时目录。

最初的延迟渲染断言假设渲染必定使读取期间的序列号发生变化，在本机上不成立；实际内容已成功渲染。最终用例验证真实读取结果、渲染次数和元数据，不假设序列号必须变化，也未添加遇到变化就丢弃内容的策略。

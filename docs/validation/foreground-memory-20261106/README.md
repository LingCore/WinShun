# 前台搜索界面的内存优化

2026-11-06，Windows x64、Qt 6.12.0、MSVC Release、D3D11、150% 缩放。

## 改动及适用范围

普通搜索框原先会同时实例化隐藏的完整搜索面板，包括筛选栏、第二套输入栏等。`Main.qml` 现在通过 Loader 在首次展开时创建面板，之后保留，避免反复创建影响切换速度。首次创建时同步当前搜索词；菜单、按键和列表访问兼容面板尚未创建的状态，也支持一开始就是完整面板的窗口。

这是普通搜索框在**尚未展开过完整面板**时的内存节省。完整面板使用后会保留，不能把此收益解释为所有运行阶段都降低同样多的内存。没有改搜索算法、索引大小、渲染质量、图形预热或工作集回收策略。

## 对照结果

同一构建目录保留优化前 exe；同一机器各运行 3 个新进程，使用真实 `Main.qml`、`Launcher` 和 `SearchEngine`，索引为 2,000 个构造的文件名。窗口正常渲染，放在屏幕外且不激活，不操作用户剪贴板，不执行内存修剪。这里不是用户整个索引及插件组合的内存测量。

下表为三个进程的中位数，MiB = 1,048,576 字节。原始读数见 `before-*.json`、`after-*.json`，汇总见 [summary.json](summary.json)。

| 场景 / 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 空搜索：私有提交内存 | 135.46 MiB | 125.91 MiB |
| 空搜索：私有工作集 | 61.27 MiB | 52.31 MiB |
| 空搜索：全部工作集 | 122.91 MiB | 113.39 MiB |
| 空搜索：窗口 QObject 后代数 | 1,715 | 852 |
| 有搜索结果：私有提交内存 | 164.24 MiB | 157.45 MiB |
| 有搜索结果：私有工作集 | 83.38 MiB | 77.68 MiB |
| 首次展开面板：私有提交内存 | 179.06 MiB | 178.16 MiB |
| 使用面板后返回搜索框：私有提交内存 | 183.79 MiB | 187.14 MiB |
| 界面组件创建时间 | 387.91 ms | 316.23 ms |
| 首次展开面板至交换首帧 | 23.67 ms | 52.41 ms |
| 后续展开面板至交换首帧 | 16.21 ms | 15.82 ms |
| 构造索引上的查询耗时中位数 | 7.67 ms | 6.71 ms |

普通搜索阶段约少 6.8–9.6 MiB 私有提交内存，少 863 个 QObject 后代；首次展开面板约增加 29 ms。后续切换相近。短查询的计时受调度影响，不据此承诺实际用户索引搜索会加速。使用面板后返回搜索框没有持续节省，本次三次运行的中位数反而高约 3.35 MiB，因此保留该行而不只列有利阶段。

基线包含任务开始时工作区已有的修改，而非直接取旧 Release。第一次探针忘记给窗口设置宽度，无法正确绘制普通搜索框；那次读数已排除，最终对照均正常绘制且探针退出码为 0。

## 第二轮：平时不显示的部件改为第一次用到时才建，面板改为后台预建（同日）

### 改动

探针加了按组件统计对象数（同时沿 QObject 树和可视树走，列表的行也算进去），据此找出一上来就建、平时却不显示的部分：

| 部件 | 原来 | 现在 |
| --- | --- | --- |
| 结果行（`ResultRow`）的系统开关、音量条 | 每行都有 | 只在开关行里建，之后保留 |
| 悬停提示（`HoverTip`） | 每个约 25 个对象（两个计时器、几组动画、气泡、测量文字） | 只留一个轻壳和一个计时器，第一次显示时才建气泡，之后保留 |
| 搜索历史下拉（`QueryHistoryPicker`） | 两个隐藏窗口和列表常驻（搜索框、面板各一套） | 第一次打开时才建 |
| 下拉菜单（`DropMenu`，排序菜单、插件卡片的“…”） | 条目和菜单框常驻 | 第一次打开时建条目（随即强制排版，供定位使用），外框 `lazy` |
| 完整面板 | 第一轮改为首次展开时才建，第一次展开因此从约 21 ms 变成约 52 ms | 启动后趁搜索框隐藏，在后台分片预建（`App::createWindow` 设 `preloadPanel`）；预建完成前就展开的，当场建完 |

结果行的对象数从 187 降到 136–155；窗口 QObject 后代数在空搜索时从 1,715（第一轮 852）降到 607，预建后为 1,301。

**试过又改回的**：结果行的 7 个操作按钮、剪贴板行（`ClipRow`）的 4 个按钮，也曾改成该行第一次显示按钮时才建。出结果时能再省约 12 MiB 私有工作集，但会卡：

- 方向键第一次移到某行要 2.2–3.5 ms，第二次 0.3 ms；
- 剪贴板第一遍滚动时，界面线程超过 2 ms 的帧从 6–7 帧增到 16–19 帧，brand 风格掉帧从 3 增到 15（以后几遍相同）。

用户的显示器是 240 Hz，一帧只有 4.2 ms。这 12 MiB 也只在显示结果期间才省，所以两处都改回随行一起建。第三轮改用整张列表借用几套按钮，省下这部分且不卡，见下文。

## 第三轮：行内按钮改为整张列表借用（2026-11-07）

### 改动

第二轮试过让每行第一次显示按钮时才建，会卡。这一轮改成每张列表只建 3 套按钮，借给正在显示按钮的那一行：

| 列表 | 原来 | 现在 |
| --- | --- | --- |
| 搜索结果（`ResultRow`） | 每行自带 7 个按钮（约 120 个对象） | 列表里一个 `RowActionsPool`，借出 `ResultActions` |
| 剪贴板（`ClipRow`） | 每行自带拖动柄和 3 个按钮 | 同样做法，借出 `ClipActions` |

- **3 套**：当前行、刚离开的悬停行、新的悬停行可能同时要按钮（Qt 先给新行发进入，再给旧行发离开）。
- **借的顺序**：先找这一行自己借过的那套，再找空闲的，再找借走它的行已不显示按钮的；都没有才新建；探针里一直是 3 套。
- **建的时机**：第一次有行要按钮时 3 套一起建。启动时就建，空搜索会多约 3.6 MiB；用到一套才建一套，建的时间又会落在悬停里。
- **行间换来换去时不新建任何东西**：
  - 按钮里的 Hook 随按钮一起建，不再 `lazy`；
  - `Glyph` 画过的复制路径图形会保留；
  - 探针检查：在各类结果行之间来回借，可达对象数前后都是 2,702。
- **其余行为不变**：
  - 删除按钮的“再点一次确认”只属于借到它的那一行，鼠标离开就取消；
  - 剪贴板的拖动柄按住时，行一直保留按钮；
  - 提示气泡、翻译上下文（`qsTranslate("ResultRow", …)`）与原来相同。

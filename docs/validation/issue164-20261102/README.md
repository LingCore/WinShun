# #164：诊断包与真实输入法对照验证

2026-11-02，Windows 11 专业版 x64（10.0.26200）。接续 [前次验证](../issue164-20261101/README.md)。

## 新材料

[报告者的新回复](https://github.com/LingCore/WinShun/issues/164#issuecomment-6559099934) 提供诊断包，以及 Windows 11 25H2、26200.8655 和三种输入法版本：微信 3.0.0、微软 10.0.26100.8328、青简 0.1.4。报告者确认三者在记事本正常，在截图和贴图标注都失败，且贴图获得焦点时输入法状态栏图标更新滞后。

诊断包含 `summary.json`、358 条 `events.jsonl` 事件和 57 行主程序日志。摘要显示 Win顺 0.17.0、管理员身份、D3D11、125% 缩放。包中没有截图插件日志，也没有可直接确定输入法失败原因的错误；不能由主程序日志推断候选窗已成功创建。原始附件及解包文件仅留在忽略的 `build/issue164-20261102/`，这里不复制报告者的私人路径。

## 实际输入法验证

使用已安装截图插件的独立副本、生成的白底图片和临时数据目录，通过真实 runner 控制协议启动插件。调用插件生产 `picture/edit` 入口打开标注窗口，不向用户现有窗口输入，不读写真实剪贴板或保存用户文件。两个对照的截图插件、Qt 运行时、输入法、图片和启动参数相同，仅更换 runner：

| 对照 | 运行器 | UI 子进程扩展点禁用策略 | 实际结果 |
| --- | --- | --- | --- |
| 旧版 | `build/release017-20261101/WinShunPluginHost.exe` | 开启（通过 `GetProcessMitigationPolicy` 读取实际插件进程） | 文字框已有焦点，物理 `n` 键直接写入英文 `n`，无候选词 |
| 修复版 | `build/search-improvements-20261101/bin/WinShunPluginHost.exe` | 关闭（同一 API 读取实际插件进程） | 物理 `n`、`i` 键出现拼音候选词，空格提交中文“你” |

输入使用 computer-use 的 `press_key`，不是 `type_text`、粘贴、UIA 设置值或注入 `QInputMethodEvent`。操作前通过 UIA 确认焦点在 `QQuickTextEdit`，提交后 UIA 读取 `Value: 你`。本机使用微信输入法，`C:/Windows/System32/wetype_tip.dll` 文件版本 **1.4.2.12**；未将此版本当作报告者的 3.0.0。

- [旧版英文直出截图](baseline-english.jpg)、[焦点和值](baseline-focus.txt)
- [修复版中文提交截图](fixed-chinese.jpg)、[焦点和值](fixed-focus.txt)

双方启动参数均为 `ui=true`、`processes=true`、普通沙箱、2048 MB、允许读写剪贴板，故此输入法对照不以进程数量差异解释结果。runner 的握手均为普通用户、中完整性。当前 runner 源码与前次隔离构建使用的源码 SHA256 一致：`a2f1a2c27ebe336df0f3c4a02452d7fc02afaf0780f7f5a4ecac14caab91b6dd`。

## 验证范围

本次覆盖生产图片编辑文字框及真实 runner 启动边界；未覆盖主程序快捷键到全屏截图选区的整条操作、贴图右键到编辑的入口、输入法状态栏实时更新，也未验证报告者的三种具体版本。微信 1.4.2.12 的对照失败及恢复支持该修复，但不代表所有输入法及用户环境都已验证。

录屏的子进程创建边界复用前次回归证据；本次附件没有新增可核对的视频输出，未把它写成完整录屏已恢复。修复尚未发布，Issue 保持打开。

## 新建议

已记录两项独立体验建议，尚未实现：

1. 滚轮调节文字大小、线宽及马赛克强度，减少固定档位和点击。
2. 贴图缩放显示百分比，并改善 200% 以上的步进。

对照 `src/capture/Geometry.cpp::zoomSteps`，当前确为 10%–200% 每格 10 个百分点，之后跳到 300%、400%、500%、600%、800%；另有像素内存预算上限。200% 后突然变大的反馈有现有代码依据。未将内存保护上限直接删除，也未在本轮把这些建议写成已完成。

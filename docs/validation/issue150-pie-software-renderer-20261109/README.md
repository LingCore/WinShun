2026-11-09，Windows 11 25H2、150% 缩放、Qt 6.12.0、MSVC 2022 x64 Release，构建目录 `build/issues-249-253-256-20261108`（沿用前两轮的目录）。

**状态：找到了一个能解释用户日志的原因，改了，并量过改动起作用。当天下午又用真实键鼠拖了文件：软件渲染下，去掉修复时拖不上去（和用户日志同一句），带修复时文件被移进收藏文件夹。** 只在 Windows 11、普通权限的进程内圆盘上测过，见“真实拖放”和“没有验证的”。

## 真实拖放（同一天下午）

做法（脚本见会话目录，结果在 `live-drag/`）：在资源管理器单独开的窗口里按住一个文件（真实的 `SendInput` 左键），按 Esc 下面那个键，指针分 12 步往上移 120 像素（150% 下 80 逻辑像素，正好是圆盘上方第一个收藏项），停 0.6 秒后松开。看文件有没有进收藏文件夹。每一步前都检查前台窗口和指针下的窗口，不对就停；按下和松开包在 `try/finally` 里，结束后核对左键已松开。Win顺 是一份单独的副本（`dist/live-82-150-20261109`）加单独的配置，普通权限，圆盘在主程序里（用户是管理员运行，圆盘在辅助进程里；两者用同一个 `DropPie` 和 `DropPieWindow.qml`，辅助进程按用户设置选同样的渲染方式）。

| 渲染方式 | 程序 | 指针下的窗口（按键后） | 结果 | 日志 |
|---|---|---|---|---|
| 软件 | 带修复 | 圆盘 | 文件移进收藏文件夹 | `1 files over it` → `dropped, moving 1 files` |
| D3D11 | 带修复 | 圆盘 | 文件移进收藏文件夹 | 同上 |
| 软件 | 去掉修复（只把那层底设为不显示，重新构建） | 资源管理器 | 文件没动 | `shown, but the drag did not come over it in 157 ms (pointer moved yes)` |

第三行的日志和用户诊断包里的那句一样。`pie-sw-fixed-over-chip.jpg` 是松开前一刻：圆盘已显示，提示“移动到 pie-dst-sw-fixed”；`pie-sw-nofill-over-chip.jpg` 是同一时刻：只有系统的拖放图标，没有圆盘。

去掉修复的那个程序只用于这一次，之后源码改回、重新构建，`git status` 里这个文件没有改动。

## 量了什么

`WinShun.exe --preview-results <目录> --drop-pie-hit [--renderer software|d3d11] [--unrevealed]`：把真的圆盘窗口在主屏中间显示不到一秒（不激活、不发任何输入、有鼠标键按着就不显示），在窗口矩形上每 6 个物理像素取一点，问 `WindowFromPoint` 这一点是不是圆盘窗口。结果写在 `drop-pie-hit.json`，本目录 `before-fix/`、`after-fix/` 各四份。

| 状态 | D3D11 改前 | 软件渲染 改前 | D3D11 改后 | 软件渲染 改后 |
|---|---|---|---|---|
| 等拖放、还没画（unrevealed） | 5251 / 5251 | **0 / 5251** | 5400 / 5400 | 5400 / 5400 |
| 已显示（revealed） | 5251 / 5251 | **2718 / 5251** | 5251 / 5251 | 5251 / 5251 |

八次测量里窗口在测量时都还显示着、实际用的渲染方式都和要求的一致、窗口都带 `WS_EX_LAYERED`（所以差别不在这个样式上）。

改前、改后两组 unrevealed 的做法不同，点数因此不一样：改前那组走的是真实的召唤路径（窗口出现在当时的指针位置，537×357）；改后那组是把从没打开过的圆盘窗口直接放在屏幕中间（540×360），原因见“探针自己出过的错”。

## 原因

`docs/pitfalls.md`“透明窗口的透明像素照样接鼠标和拖放”一条写的是“Qt Quick 的透明窗口是整块矩形参与命中测试的，不按像素的透明度”。上表说明这只在 D3D11 下成立；软件渲染下全透明的像素不算这个窗口的。圆盘又是等 `DragEnter` 才画（`DropPie::dragEnter` 里才 `reveal`），于是软件渲染下：没画 → 找不到窗口 → 拖放进不来 → 永远不画。那条说明已在原处补上限定，并新增了一条。

## 没有验证的

- ~~没有在软件渲染下真的拖一次文件。~~ 下午做了，见“真实拖放”。
- **没有在 Windows 10 上量过或拖过。** 用户是 Windows 10 21H1。
- **没有测管理员运行时的辅助进程。** 真实拖放用的是普通权限、圆盘在主程序里的那条路。

- **不带修复时，新做法（直接显示在屏幕中间）的 unrevealed 没有看到它失败。** 看到失败的是召唤路径那种做法。
- **那层 1/255 的底肉眼看不看得出，没有比对过。** 按混合公式，它下面的桌面像素每个通道最多变暗 1/255。
- 用户内存 16 GB，默认应该是 D3D11，为什么是软件渲染不知道（可能是自己在设置里选的）。

## 探针自己出过的错（读中间结果时要知道）

- 最初探针在日志行里又量了一次“中心是否命中”，那时窗口已经藏起来了，所以日志写“centre no”，而 JSON 里是命中。已改成日志只引用 JSON 里的值；那两次的日志没有留。
- unrevealed 起初是通过真实召唤来做的：窗口出现在指针位置，150 ms 后指针不在原处就自己藏起来。用户在用电脑、指针在动，有一次两种渲染都量到了已经藏起来的窗口（探针报“NOT MEASURED”，退出码 6，没有被当成结果）。因此改成不依赖指针的做法。
- 探针显示的窗口是真的放下目标。已显示（revealed）的那种在显示期间能接受放下，目标是随探针删除的临时文件夹；所以探针在有鼠标键按着时不显示。第一批运行（10:22 之后，D3D11 和软件渲染各一次，都是 revealed）还没有这个保护；10:25 起的每次运行都有。

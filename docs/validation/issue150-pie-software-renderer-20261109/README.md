# #150：软件渲染下收藏圆盘出不来

2026-11-09，Windows 11 25H2、150% 缩放、Qt 6.12.0、MSVC 2022 x64 Release，构建目录 `build/issues-249-253-256-20261108`（沿用前两轮的目录）。

**状态：找到了一个能解释用户日志的原因，改了，并量过改动起作用。没有在软件渲染下真正拖过一次文件，所以不能说“已修好”。** 没验证的部分见本文“没有验证的”一节。

## 用户的诊断包说了什么

Dorl121 在 2026-11-07 发的包（0.22.0，Windows 10 21H1，以管理员身份运行，圆盘在 `DropPieHelper` 进程里，150%）里，`summary.json` 的渲染方式是 `software`，日志里五次尝试都是同一种结局：

```
2026-11-07T19:03:27.612 Drop pie helper (info): Drop pie: its key pressed at 631,287
2026-11-07T19:03:28.614 Drop pie helper (warning): Drop pie: shown, but the drag did not come over it in 860 ms (pointer moved yes)
2026-11-07T19:03:28.614 Drop pie helper (info): Drop pie: hidden, the drag did not come over it
```

按键收到了，窗口也显示了，但拖放从来没进到窗口里。其中一次指针没动、等满一秒（`pointer moved no`，1041 ms）也没等到。圆盘要等拖放进来才开始画，所以用户看到的是“什么都没出来”。

## 量了什么

`WinShun.exe --preview-results <目录> --drop-pie-hit [--renderer software|d3d11] [--unrevealed]`：把真的圆盘窗口在主屏中间显示不到一秒（不激活、不发任何输入、有鼠标键按着就不显示），在窗口矩形上每 6 个物理像素取一点，问 `WindowFromPoint` 这一点是不是圆盘窗口。结果写在 `drop-pie-hit.json`，本目录 `before-fix/`、`after-fix/` 各四份。

| 状态 | D3D11 改前 | 软件渲染 改前 | D3D11 改后 | 软件渲染 改后 |
|---|---|---|---|---|
| 等拖放、还没画（unrevealed） | 5251 / 5251 | **0 / 5251** | 5400 / 5400 | 5400 / 5400 |
| 已显示（revealed） | 5251 / 5251 | **2718 / 5251** | 5251 / 5251 | 5251 / 5251 |

八次测量里窗口在测量时都还显示着、实际用的渲染方式都和要求的一致、窗口都带 `WS_EX_LAYERED`（所以差别不在这个样式上）。

改前、改后两组 unrevealed 的做法不同，点数因此不一样：改前那组走的是真实的召唤路径（窗口出现在当时的指针位置，537×357）；改后那组是把从没打开过的圆盘窗口直接放在屏幕中间（540×360），原因见“探针自己出过的错”。

## 原因

`docs/pitfalls.md`“透明窗口的透明像素照样接鼠标和拖放”一条写的是“Qt Quick 的透明窗口是整块矩形参与命中测试的，不按像素的透明度”。上表说明这只在 D3D11 下成立；软件渲染下全透明的像素不算这个窗口的。圆盘又是等 `DragEnter` 才画（`DropPie::dragEnter` 里才 `reveal`），于是软件渲染下：没画 → 找不到窗口 → 拖放进不来 → 永远不画。那条说明已在原处补上限定，并新增了一条。

## 改动

- `src/app/qml/DropPieWindow.qml`：用软件渲染绘制时（`GraphicsInfo.api`，看实际用的，不看设置）铺一层满窗口、不透明度 1/255 的底，放在随 `reveal` 淡入的那层外面。D3D11 下这层不显示。
- `src/app/Preview.cpp`、`Preview.h`：`--drop-pie-hit` 探针。
- `tests/CMakeLists.txt`：`tst_droppiehit_{revealed,unrevealed}_{d3d11,software}` 四个测试（串行；退出码 5 表示有鼠标键按着、算跳过；6 表示没量成、算失败）。

- 不带修复（把 `DropPieWindow.qml` 换回已提交的版本后构建，10:30）：D3D11 两种状态通过，软件渲染两种状态失败（退出码 4），即上表“改前”两列。
- 带修复，由 CTest 驱动（10:37）：`ctest -R tst_droppiehit`，4 个全过，即上表“改后”两列。
- 召唤路径的 unrevealed 在带修复时也量过两次（10:27、10:29），都是 5251 / 5251；其中 10:27 那次和 10:30 不带修复的那次窗口位置相同（1632,756）。这两次的结果文件后来被覆盖了，只在会话输出里有，本目录没有。

测试用的程序是 10:33:39 构建的；之后源码只改了 `Preview.h` 里 7 行注释，当前源码另外完整构建通过（10:38）。构建编的是整个工作区，里面还有另一轮未提交的改动（Logo 位置等），与圆盘无关但确实在这个程序里。

## 没有验证的

- **没有在软件渲染下真的拖一次文件。** 量的是 `WindowFromPoint`；OLE 拖放找目标是不是完全按它来，是推断，依据只有用户日志里“拖放没进来”和 pitfalls 里 D3D11 下的实测。真实拖放要接管鼠标几秒，测试时用户正在用电脑，没有做。
- **没有在 Windows 10 上量过。** 用户是 Windows 10 21H1。
- **不带修复时，新做法（直接显示在屏幕中间）的 unrevealed 没有看到它失败。** 看到失败的是召唤路径那种做法。
- **那层 1/255 的底肉眼看不看得出，没有比对过。** 按混合公式，它下面的桌面像素每个通道最多变暗 1/255。
- 用户内存 16 GB，默认应该是 D3D11，为什么是软件渲染不知道（可能是自己在设置里选的）。

## 探针自己出过的错（读中间结果时要知道）

- 最初探针在日志行里又量了一次“中心是否命中”，那时窗口已经藏起来了，所以日志写“centre no”，而 JSON 里是命中。已改成日志只引用 JSON 里的值；那两次的日志没有留。
- unrevealed 起初是通过真实召唤来做的：窗口出现在指针位置，150 ms 后指针不在原处就自己藏起来。用户在用电脑、指针在动，有一次两种渲染都量到了已经藏起来的窗口（探针报“NOT MEASURED”，退出码 6，没有被当成结果）。因此改成不依赖指针的做法。
- 探针显示的窗口是真的放下目标。已显示（revealed）的那种在显示期间能接受放下，目标是随探针删除的临时文件夹；所以探针在有鼠标键按着时不显示。第一批运行（10:22 之后，D3D11 和软件渲染各一次，都是 revealed）还没有这个保护；10:25 起的每次运行都有。

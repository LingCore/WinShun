## 读共享的并发与文件管理器卡顿（实测）

服务器：WSL2 里的 Alpine 3.22 + Samba 4.21.9（`share-load/setup.sh`），20×60 个文件夹各 100 个文件，约 12 万项。“后台”是 `wsbench --share`（与 Win顺 相同的读取代码），“文件管理器”是 `share-load/probe.ps1`：另一个进程每 0.2 秒打开并列出一个随机文件夹。两者在服务器上是同一个 `smbd` 进程（`smbstatus` 只有一个 PID）。

| 服务器 | 后台同时读 | 读完整个共享 | 期间打开一个文件夹：中位 / p90 / 最长 |
|---|---|---|---|
| 快盘（缓存热） | 无 | — | 2.8 / 3.3 / 6.0 ms |
| | 固定 1 | 2.7 s | 2.7 / 3.3 / 3.5 ms |
| | 固定 8 | 1.5 s | 10.5 / 15.8 / 15.8 ms |
| | 固定 16（原来的首次收录） | 1.3 s | 20.7 / 21.9 / 21.9 ms |
| | **现在（有人在）** | 1.9 s，平均 1.3 个 | 3.0 / 8.0 / 8.0 ms |
| 慢盘（每次读盘 10 ms，`slowdisk.sh`，缓存冷） | 无 | — | 26.7 / 50 / 62 ms |
| | 固定 1 | 19.5 s | 22 / 115 / 183 ms |
| | 固定 8（原来的核对） | 18.8 s | 109 / 200 / 879 ms |
| | 固定 16 | 18.9 s | 184 / 302 / 2080 ms |
| | **现在（有人在）**，3 次 | 19.9～20.5 s，平均 1.2～1.5 个 | 18～26 / 83～118 / 272～315 ms |
| 快盘 + 5 ms 网络延迟（`tc netem`，模拟无线/远程） | 固定 1 | 21.4 s | 17.4 / 18.2 / 23.6 ms |
| | 固定 16 | 1.6 s | 19.8 / 28.4 / 28.4 ms |
| | **现在（有人在）** | 6.1 s，结束时已加到 8 个 | 17.4 / 18.5 / 19.3 ms |

- 等待时间随“同时读几个”成正比，而服务器慢在磁盘时读完并不更快：多开只是让别的程序多等。
- 另一种慢盘模型（cgroup 限每秒 100 次读，`serve.sh hdd 100`）下固定 1/8/16 个时最长一次打开分别等了 9、30、60 秒，与反馈说的“卡死”相符；该限速方式自身会成批停顿，数值只作旁证。
- 整套 `ShareIndexer`（`wsbench --share … --indexer`，慢盘）：`WINSHUN_USER=present` 时 25.5 / 90 / 271 ms，`away` 时 202 / 363 / 1909 ms，两次都收录 131061 项。
- 代价：快速局域网服务器上，有人在时首次收录比原来慢（上表 1.9 s 对 1.3 s；本机 Windows 共享回环 3.0 s 对 1.5 s），离开电脑后恢复全速。
- 没验证到的：真实 NAS（群晖等）、局域网上的真实 Windows 服务器（只有本机回环）、真实无线或 VPN（只有模拟延迟）。

### 第二轮：还能再压多少

慢盘换成 17 万项（其中 10 个文件夹各 5000 个文件），探测改为每 50 毫秒一次，每种条件交替跑 3 遍（每遍约 250 次打开）：

| 后台 | 读完 | 打开一个文件夹：中位 / p90 / p99 / 最长 |
|---|---|---|
| 无 | — | 23 / 35 / 55 / 73 ms |
| 固定 1 个，缓冲区 64 KB | 25.5 s | 19～24 / 101～119 / 210～262 / 261～330 ms |
| 固定 1 个，缓冲区 4 KB | 25.5 s | 13～15 / 54～60 / 133～152 / 141～176 ms |
| 现在（有人在，平均 1.6 个） | 24.6 s | 29～35 / 126～145 / 250～265 / 275～325 ms |
| 固定 16 个 | 23.8 s | 190 / 306 / 2241 / 2241 ms |

- 一次只读 1 个就是下限：总有一个我们的请求在服务器上，别人的请求要等它完。“现在”的做法离这个下限约 1.3 倍（差在试宽的那几个窗口），离原来的 16 个差一个数量级。
- 缓冲区改小没有采纳。每个文件夹的第一批是 Windows 按自己的大小取的（100 个文件的文件夹，4 KB 与 64 KB 往返次数相同），之后才按我们的缓冲区。4 KB 只对几千个文件的大文件夹有用，能把尾部减半；但加 5 毫秒延迟后读 10 个 5000 文件的文件夹要 7.5 秒，64 KB 只要 0.9 秒。
- 要低于这个下限只能让服务器空着，所以每小时的自动核对改为到点后等用户离开再读（最多等 2 小时），那时全速读也不碍事。这一点只有 `tst_core::sharePassDue` 覆盖判断逻辑，没有等上一小时实跑。
- 第一轮里限流放在“领了文件夹之后”，改为领之前（`Crawler::Gate`），读取顺序与单线程一致，`tst_core::crawlerGateKeepsTheOrder`。
- 测量时要注意：刚建好的文件系统第一次清缓存清不干净（那一遍 17.6 s，之后每遍 24～26 s），第一遍不能算数；条件之间要交替重复。
- 外部资料里没有采纳的两点：“整个共享的变化监听会耗尽 NAS 的 inotify”与本项目此前实测不符（NAS 本机在子文件夹里的改动 Samba 并不通知，说明没有逐层挂监听）；“后台 I/O 优先级”对 SMB 请求有没有作用没有证据。缩小列目录缓冲区（64 KB → 8 KB）在一次测量里 p90 从 115 降到 54 ms，样本太少，未采纳。

# #467 截图时主程序和截图插件的内存尖峰

2026-11-26，Hyper-V 虚拟机 Windows 10 22H2（19045.6456，1920×1080，100% 缩放，4 个虚拟处理器，`Renderer=d3d11` 走 WARP）。对照：安装版 0.48.0 + 截图插件 1.1.38；改后替换 `WinShun.exe`、`WinShunCapture.exe`、`WinShunCaptureApp.dll`（`build\issue467b`）。设置窗口关着，Win顺 在后台空闲。

## 原因

用临时打点（每一步记 `PagefileUsage` 和 `PeakPagefileUsage`，未入库）在虚拟机里量整屏截图复制的全过程：

| 步骤（主程序） | 提交内存 | 说明 |
|---|---|---|
| 收到图片前 | 103 MB | |
| 写入剪贴板途中 | 168 MB | 解码刚编好的 PNG、转格式、像素数组、两份 DIB 字节数组、两份剪贴板内存块 |
| 写入完成 | 137 MB | 剪贴板持有 `CF_DIB`、`CF_DIBV5` 两份像素 |
| 识别图片文字：找文字行 | **343 MB** | 检测模型一次看整张 1920×1080，约 80 字节/像素 |
| 识别文字、找二维码 | 不再升高 | |
| 2 秒后 | 139 MB | |

- 截图插件框选后的“智能打码”预识别是同一个检测步骤，所以插件也有同样的尖峰。
- 同一张图，插件识别一遍，主程序为剪贴板搜索又识别一遍。

## 改动

- **分条检测**（`PaddleOcr`，主程序和截图插件共用）：找文字行的条高从 2000 行降到 512 行（重叠 160 行不变）；有高过重叠区的大字被条边切到时，那一块按原来的 2000 行重新检测。
- **识别结果复用**：截图插件预识别读到的文字随图片交给主程序（`clipboard_add_image` 的 `words`），主程序补上二维码内容后直接保存，不再识别。标注过的截图、预识别还没读完就复制的截图照常由主程序识别。
- **写剪贴板少拷贝**：截图的像素直接随写入请求交给剪贴板线程，`CF_DIB` / `CF_DIBV5` 逐行写进剪贴板的内存块；不再解码 PNG，不再经三份中间数组。

## 实测（真实峰值）

真实快捷键 + 真实鼠标拖出整屏选区（1917×1077），各进程的 `PeakPagedMemorySize64`（进程启动以来的提交内存峰值）：

| 时刻 | 0.48.0 主程序 / 截图插件 | 改后 主程序 / 截图插件 |
|---|---|---|
| 后台空闲（启动时的峰值） | 129 / 83 MB | 122 / 82 MB |
| 遮罩出现 | 129 / 112 MB | 122 / 113 MB |
| 选好区域 4 秒（预识别完成） | 129 / **336 MB** | 122 / **251 MB** |
| 复制（预识别已完成） | **340** / 336 MB | **148** / 251 MB |
| 再截一张，选好立刻复制（主程序自己识别） | 341 / 336 MB | **246** / 251 MB |

- 截图插件框选时的峰值：+224 MB → +138 MB。
- 主程序复制截图时的峰值：+241 MB → +50 MB（文字复用时）或 +148 MB（主程序自己识别时）。
- 复制后剪贴板里的图，新旧两版读出来一致：格式列表相同（`PNG`、`image/png`、`CF_DIB`、`CF_DIBV5` 等），尺寸 1917×1077，5 个取样像素（四角附近与中心）逐值相同。
- 复用文字的那一条在 `clipboard.db` 里有文字（161 个字符，与主程序自己识别的长度相同）。

改后第一次运行（刚换完文件）在复制后 20 秒左右两个进程的提交内存同时有过一阵起伏、第二次截图没截上；随后两次重跑都没有再出现，原因没有查明。

## 识别结果对比

`WinShunOcrTest.exe` 用本机剪贴板历史里的 80 张图加 2 张自带示例图，新旧条高各读一遍，只比较每张图的行数和字数（不输出内容）：

| | 条高 2000 | 条高 512 |
|---|---|---|
| 行数、字数完全相同的图 | — | 47 / 82 张 |
| 其余 35 张的差异合计 | — | 行数差 12（共 1165 行），字数差 220（共 24,034 字，约 0.9%），有多有少 |
| 读图过程最高提交内存 | 411 MB | 218 MB |
| 80 张图总用时 | 24.6 秒 | 27.2 秒 |
| 触发“按 2000 行重新检测”的图 | — | 0 张 |

没有标准答案可比，只能说明两者差异很小、没有成片丢行。

## 测试

- `ctest -R "^(tst_ocr|tst_clipimage|tst_clipboard|tst_capture|tst_editor|tst_idletrim)$"` 通过。新增：`tst_ocr` 的 `screenshotLookedAtInStrips`（每次检测高度 ≤ 512、每行只读到一次）和 `tallTitleAcrossAStrip`（260 像素高的标题跨条边：触发重新检测，读到一次）；`tst_clipimage` 的 `dibRowsFromEach32BitFormat`（三种 32 位格式逐像素还原）和 `pixelsInHandAreWrittenAsTheyAre`（需要私有剪贴板，本机直接运行时被跳过）。
- 顺带修了 `tst_clipimage` 里两处早先遗留的失败（`ClipRow` 新增的必填属性 `hotkey` 测试里没给）。
- 未测：4K 或多显示器下的实际数值（检测前宽度先缩到 2000，按像素推算与 1080p 相近）；带透明度的图片实际粘贴到其他程序里的效果（只有单元测试）。

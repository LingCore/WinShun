# 2026-11-12：#280 闲置后呼出搜索框、剪贴板要等一下

分支 `issue280`。Qt 6.12.0 / MSVC Release，本机（32 个逻辑处理器、内存充裕、NVMe 固态盘、150% 缩放、D3D11 渲染）。只跑了这次涉及的测试，没有跑全量 ctest。

## 结论

- 0.24.0 的做法（闲置 20 秒后清空整个工作集，按键时让 Windows 成批预读）不够：窗口要用的页照样得一页页回来。内存不紧张时只多十几毫秒；内存紧张时，本机固态盘上搜索框也要 100 ms 以上、剪贴板 70 ms 以上，机械硬盘或更紧的内存会到秒，这就是 #280。
- 现在交还内存时留下呼出窗口要用的页，其余照旧交还。内存紧张时搜索框 108.5 → 34.9 ms，剪贴板 82.3 → 14.6 ms，和刚用过差不多；内存不紧张时也回到刚用过的水平。
- 代价：闲置时任务管理器里的内存从约 5 MB 变成 31–37 MB。
- 真实热键（外部程序按 Ctrl+F22，0.25.0 整包的副本）：闲置后 0.25.0 原版 57–73 ms，新版 38–57 ms，刚用过 33–47 ms。
- 代价按真实热键那组看是 35–38 MB（呼出时带着上次搜索的结果，要留的页多一些）。
- 没解决的：启动后的第一次呼出还是旧的速度（那时还没学到要留哪些页，表里新版最大值 139.8 ms 就是这一次）。试过在第一次交还后把窗口隐藏着画一遍来学，收益太小，没有采用，见下面。Windows 自己把工作集清掉时（`windows` 一行），新旧一样，仍靠按键时的预读。
- 没测的：真正的内存吃紧（Windows 按页龄回收工作集）。这里只用“清空备用列表”模拟了“交还出去的页被别的程序拿走”这一半；另一半要把整机内存占满，会拖垮同时在跑的其他工作，没有做。

## 测法

`WinShun.exe --probe-runtime <目录> --idle-open-check --with-clipboard --renderer d3d11 --idle-open-index "C:/;F:/"`（`src/app/IdleOpenProbe.cpp`）：正式的 `App`，和正在运行的 Win顺 并存，索引 C: 和 F:（约 233 万条）。每次呼出走热键的同一条路径（`beginTrigger` 加切换），记从调用到窗口揭开遮罩的时间（`seen_ms`）、这期间的缺页数、之前的私有工作集，以及前一秒到显示为止整机的 CPU 占用。不发任何按键；每次呼出前等键盘鼠标空闲 3 秒。

每一轮对搜索框、剪贴板各做：打开一次再关掉 → 等 `IdleTrim` 自己交还（`idle`）→ 呼出并计时 → 关掉 1 秒后再呼出并计时（`warm`）。最后各做 3 次“Windows 清空了工作集”（`EmptyWorkingSet`，不告诉 Win顺）后的呼出（`windows`）。

- **改前（baseline）**：main 的 48359017 加这个探针。**改后（keep）**：本分支。两个版本交替跑。
- 别的会话在编译时，时间会翻倍。整机 CPU 占用超过 30% 的呼出不算，表里记在“忙”一列。
- 为了一轮多量几次，`--idle-open-after-use` 把“用过之后等多久交还”从 20 秒缩到 3 秒；“真实闲置”一组用原来的 20 秒，交还后再静置 40 秒。
- **内存紧张**：`--idle-open-pressure <目录>`，交还之后请提权的助手（[purger.ps1](purger.ps1)）把修改页写出、清空备用列表（`NtSetSystemInformation(80)` 的 3 和 4），相当于 Windows 把这些页给了别的程序，再用就要从页面文件读。

汇总：`python summary.py data <组名>`，原始数据在 [data/](data/)。

## 结果

时间是中位数（最小–最大），毫秒；n 是算进去的次数。

### 内存紧张（交还后清空备用列表）

| 窗口 | 改前 | 改后 | 刚用过（改前 / 改后） |
|---|---|---|---|
| 搜索框 | 108.5（101.7–166.8），n=5，缺页 23,148 | 34.9（21.2–139.8），n=5，缺页 241 | 28.8 / 24.6 |
| 剪贴板 | 82.3（68.9–125.0），n=4，缺页 5,537 | 14.6（12.4–123.9），n=5，缺页 239 | 11.4 / 12.1 |

改后的两个最大值：搜索框 139.8 ms 是启动后第一次（交还时还什么都没留，之前私有内存 4.8 MB）；剪贴板 123.9 ms 是第二轮，有几百页还没满“连续两次”、没留下。从第三轮起搜索框 21–35 ms，剪贴板 12–19 ms。

### 内存不紧张

| 组 | 窗口 | 改前 | 改后 | 刚用过（改前 / 改后） |
|---|---|---|---|---|
| 3 秒后交还 | 搜索框 | 47.5（44.1–49.7），n=3，忙 5 | 31.6（25.6–49.8），n=8 | 26.4 / 29.4 |
| 3 秒后交还 | 剪贴板 | 15.5（12.5–19.2），n=4，忙 4 | 8.8（7.4–9.9），n=8 | 8.8 / 8.1 |
| 20 秒后交还，再静置 40 秒 | 搜索框 | 32.7（31.7–38.8），n=3，忙 1 | 27.7（21.9–30.7），n=4 | 23.8 / 25.3 |
| 20 秒后交还，再静置 40 秒 | 剪贴板 | 17.7（12.6–46.6），n=3，忙 1 | 10.5（9.1–17.3），n=4 | 13.9 / 7.7 |

最终版本单独再跑一组（3 秒后交还）：搜索框 32.8（27.1–37.3），n=6；剪贴板 8.7（7.1–14.3），n=6。

### 闲置时的内存

呼出之前的私有工作集（任务管理器“内存”一栏）：改前 3.8–7.7 MB，改后 30.8–37.0 MB。保留集连共享的 DLL 页在内是 53–56 MB（日志 `Idle trim: 92 MB, keeping 55 MB`），15 轮里从 50 MB 涨到 56 MB。

### Windows 自己清空工作集

改前改后一样（搜索框 28–40 ms，剪贴板 12–15 ms）：这时保留的页也被清了，靠按键时的预读，这部分没有变。

## 真实热键

[live.ps1](live.ps1)：把 `dist\release025\WinShun`（0.25.0 发布包）复制成副本，独立配置（`--profile`，热键 Ctrl+F22，关掉双击、剪贴板、右键菜单、对话框条、历史、内容索引、自动更新），普通权限启动；索引走已安装的服务，是整机的真实索引。[ab-type.cs](ab-type.cs)（在 #265 的 `ab.cs` 上加了“窗口在前台时输入 exe 三个字母”）用 `SendInput` 按 Ctrl+F22，每 1 ms 看窗口有没有揭开遮罩。不做一次搜索的话，这份空配置呼出一次只多 25 MB，到不了交还的阈值，量不到。每次按键前等键盘鼠标空闲 3 秒，隔 27 秒一次（20 秒后交还）。原版和新版只换 `WinShun.exe`。

| | 0.25.0 原版 | 新版 |
|---|---|---|
| 启动后第一次 | 41.9 ms，缺页 10,341 | 53.8 ms，缺页 9,507 |
| 刚用过（5 次） | 38.3–64.2 ms | 32.8–43.1 ms |
| 闲置 27 秒后（6 次） | 57.4、58.0、59.0、61.1、61.5、72.7 ms，缺页约 37,800 | 38.5、40.3、40.8、42.4、48.1、56.6 ms，缺页约 24,300–28,400 |

新版剩下的两万多次缺页是文件索引的页，在搜索线程和预读线程上。日志里保留集 42 → 61 → 65 MB（含共享页）：启动后第一次呼出是空搜索框，以后带着上次搜索的结果，要留的多 20 MB。最初“涨过首次的一半就退回”卡在 64 MB 上，43 → 61 → 64 → 43 来回摆；改成两倍后稳在 61–65 MB。原始输出：[data/hotkey-release025.txt](data/hotkey-release025.txt)、[data/hotkey-new.txt](data/hotkey-new.txt)（新版是改成两倍之后的那次）。

测完用副本自己的 `--quit` 退出，右键“用 Win顺 搜索此处”的三处注册表项按测前导出的恢复，自启动任务仍指向 `C:\Program Files\WinShun\WinShun.exe`。

## 启动后第一次呼出：隐藏着画一遍来学（没有采用）

想法：第一次交还时什么都没学到，全部交了出去；交还完马上让窗口隐藏着画一帧（`prewarmLauncher`、`prewarmClipboard`，启动时和睡眠醒来后本来就这么做），把这一帧用到的页记成保留集。探针在启动后第一次交还、再清空备用列表之后量每个窗口的第一次呼出（`first`），各 3 次：

| 窗口 | 不画 | 画一遍 |
|---|---|---|
| 搜索框 | 183.2、206.2、259.4 ms，缺页 7,849–9,817 | 148.4、163.5、210.6 ms，缺页 5,620–8,909 |
| 剪贴板 | 115.9、129.9、130.8 ms，缺页约 4,500 | 100.7、141.3、169.0 ms，缺页约 3,400 |

画一遍只学到 24 MB，真的第一次呼出还要取回五千到九千页：它用到的东西多数是当场才建的（按需加载的界面、输入法、第一次搜索），隐藏着画一帧碰不到。五十来行代码换不到两成，撤掉了。数据：`data/first-plain-*.json`、`data/first-rehearsed-*.json`。

## 保留集涨过头时退回最初那份

原来的做法是涨过头就清空、从下一次呼出重新学，那一次呼出又是“什么都没留”的速度。现在只丢掉后来加进去的，最初学到的那份留着；还在用的页两次呼出后又回来。上限是首次的两倍（至少多 32 MB）。

## 过程里量过、最后没用的

- **按键时给工作集拍快照，显示后相减**：学得精确，但在界面线程上占 3.3–4.4 ms。改成显示后在后台线程取一次、减去保留集。
- **用到过一次就留**：每轮多留约 2 MB（开窗时新分配、以后不再用的页），10 轮 44 → 63 MB。改成连续两次用到才留。
- **预读索引和窗口同时进行**（原来的做法）：内存紧张时窗口 62.7 ms；挪到窗口显示之后是 32.8 ms。
- **“被移出的页闲置后被压缩”的猜想**：[rest.cpp](rest.cpp) 把 80 MB 移出工作集，0、5、30、60、120 秒后取回分别是 13.6、12.6、12.9、13.6、18.0 ms，没有区别。

## 系统行为的依据

[evict.cpp](evict.cpp)：对没锁定的页调 `VirtualUnlock`。

- 64 MB 里移出中间 16 MB：正好少 4,096 页，1.1 ms，再读内容还在。
- 一次调用跨两块相邻的分配：两块都移出。
- 范围中间有已释放的页：其余照样移出。
- kernel32 的映像页：201 → 4 页。
- 范围里有保护页：保护位还在。
- 32,768 次单页调用 20.5 ms；一次调用移出 128 MB 是 8.5 ms；清空整个工作集（256 MB 以上）21.6 ms。

## 自动测试

`tst_hotpages`（14 项，全过）：页范围的并、差、交和随机数据对照；只移出指定的页、其余留在工作集、内容不变；锁定的页和保护页不动；已释放的内存不出错；“连续两次才留”和“涨到两倍就退回最初那份”。

另外编译通过：`WinShun`、`WinShunCapture`、`WinShunCaptureApp`、`WinShunOcrSearchApp`。两个插件也编译 `IdleTrim.cpp`，它们不传保留集，闲置时仍是清空整个工作集。截图插件自己也用 `HotPages` 在开始截图时预读，这次只把它改到新接口上（清空后的第一次截图记下用到的页，以后连续两次用到的才加），没有让它留页；实测见上面“截图插件”。图片文字搜索插件只确认了能编译。

变基到 main（6e70cf33）之后重新编译，单元测试再跑一遍，探针再跑 3 轮：12 次呼出都出来了，闲置后搜索框 25–41 ms、剪贴板 8–17 ms（当时别的会话在编译，整机 CPU 占用 14–50%）。

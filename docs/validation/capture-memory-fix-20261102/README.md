# 截图插件内存优化验证（2026-11-02）

承接[首次核查](../capture-memory-20261102/README.md)。这次修改生产实现，并使用独立配置和真实截图插件验证；未替换已安装插件，未退出用户的 Win顺、截图或编辑窗口。

## 改动与原因

- 普通 SDR 单张截图复用已有的 BitBlt 路径，不再常驻 WGC 设备和 capture item。HDR 保留 WGC 与 scRGB 映射；长截图需要连续帧时按需创建 WGC，在流结束后释放 SDR 设备。录屏继续使用自己的捕获进程和设备。
- 编辑、OCR、设置、长截图与录屏面板隐藏 20 秒后，关闭 Qt 的 persistent scene graph / graphics 提示并请求释放图形资源。短时间重开仍复用；窗口、原生 HWND 和 QML / 模型对象保留。截图遮罩继续预热，保持热键响应。
- BitBlt 的 GDI 对象使用作用域清理；读取像素前解除位图的 DC 选中状态，符合 [GetDIBits 的要求](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-getdibits)。
- 完整窗口测试发现当前工作树的 `WindowEdge.qml` 依赖 `WindowMask`，截图插件此前未注册该类型和着色器，编辑等五种窗口均无法加载。补齐依赖并共用 CMake 函数后，再开始内存对照。两份对照构建均包含此修复。

[Qt 文档](https://doc.qt.io/qt-6/qquickwindow.html#releaseResources) 说明资源回收取决于渲染循环；本次在默认 threaded D3D11 路径验证。没有切换 basic 循环、共用外部 D3D 设备或改变卡片统计口径。

## 整套插件对照

Windows 本机、Qt 6.12.0 / MSVC Release、单屏 2560×1600、150%、SDR。两份插件使用同一宿主 Qt、同一代码快照及生成的 820×420 测试图，独立配置关闭热键和 PrtScn 接管。原版只还原本次内存管理改动；其他改动和 WindowMask 依赖修复相同。

单位为 MiB（界面习惯显示 MB）。`PrivateUsage` 是私有提交，`WorkingSetSize` 是总工作集，包含共享页面；二者不能混用。见 [Windows 定义](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)。

| 同一操作阶段 | 原版私有提交 | 修复版私有提交 | 原版总工作集 | 修复版总工作集 |
| --- | ---: | ---: | ---: | ---: |
| 加载及五种窗口 QML 自检后 | 139.36 | 125.26 | 105.35 | 94.27 |
| 打开测试图的编辑窗口 | 236.48 | 220.63 | 180.52 | 170.45 |
| 编辑窗口关闭、闲置回收后 | 224.80 | 182.09 | 30.47 | 4.25 |
| 新进程连续三次普通截图、取消并闲置后 | 193.18 | 160.80 | 8.15 | 7.54 |

原版和修复版的工作集都会被现有 `IdleTrim` 回收；这不是此次新增的收益。私有提交分别减少约 43 MiB（编辑窗口闲置）和 32 MiB（普通截图循环），约 19% / 17%。不同阶段分配不同，不能把表中各行差值相加。采样不是峰值；没有声称消除所有驱动堆缓存或证明长期无泄漏。原始有效采样见 [measurements.json](measurements.json)。

最后一组截图均通过生产 initialize / action 协议开启并取消。原版遮罩出现耗时为 105、51、51 ms，修复版为 94、57、57 ms。时间从 `Capture::start` 至遮罩完成显示，含抓帧和窗口枚举，不含协议 action 有意等待启动器消失的 200 ms，不是物理按键端到端延迟。首次与预热后的数字分开看。详情见 [workflows.json](workflows.json)。

独立生产 Grabber 探针连续六次截图并释放图片：原版最后私有提交 67.57 MiB，修复版 2.68 MiB；修复版普通截图 31–35 ms。这个数字只属于抓帧探针，**不是整个插件只有 3 MiB**。两次 WGC 流均能按需创建、读到尺寸正确的帧并结束。HDR 模拟开关强制走 FP16 WGC，六次均验证到 HDR 原始像素；没有真实 HDR、多屏硬件的本次验证。

## 验证结果与历史失败

- 最终构建成功；[13 组回归全部通过](regression-tests.txt)：抓屏状态 / HDR 算法、录屏媒体管线，以及 100/125/150/175/200% 的软件和 D3D11 截图 UI。新增 threaded D3D11 回归验证快速重开保留场景图、闲置后确实失效、再次打开 HWND 不变且冻结图像素不变。
- 五种真实 QML 窗口均加载成功。编辑器实际显示测试图，关闭、等待回收后重新打开，画面正常；没有通过此项声称验证了中文输入法候选交互。
- 最终构建的真实录屏预览完成两段硬件 H.264 MP4（110 / 36 帧），包括准备、暂停、保存和“再录一段”。长截图取消路径通过，面板和帧流退出。
- 最终构建的自动长截图为 900×4440，最大通道差异 1 级，原有严格阈值检查通过，退出码 0。前一轮手动 / 自动预览曾失败：3996000 像素中 17 个像素超过 1 级，最大 2 级；同轮原版与当时修复版自动长图 **0 个像素不同**。此项历史失败保留在 workflows.json，阈值始终未放宽。当前证据不能区分这次微小波动的全部成因，未将其归因为内存修复。
- 第一次错误地把自动完成与取消两个互斥预览选项同时传入，测试失败；随后取消单独验证通过。录屏隔离预览最初缺少宿主 Shapes 模块搜索路径；显式设置 `QML2_IMPORT_PATH=<宿主>/qml` 后完成。软件离屏回归使用 SDK 的 `QT_PLUGIN_PATH`，避免已部署目录只有 windows 平台插件的问题。这些环境失败不计为通过。

生产 Grabber 源码探针及编译脚本保留在本目录；`build-grabber.ps1 -QtDir <Qt SDK>` 已从记录目录编译、运行成功，`-SimulateHdr` 可走模拟 HDR，`-GrabberSource ./grabber-baseline.cpp` 可重建原抓帧器。验证输出和二进制在 `build/capture-memory-fix-20261102/`；最终修复 DLL SHA256 为 `8679572A0EEF542FB82574045F06F123809302B2F1C73981B7E41100C6D5C134`，对照 DLL 为 `CB8279B8671CD37E849FC8D19C668BA718EA9627506F7868F5FCFEA5982F3B45`。临时实例仅使用测试配置；结束后退出或清理本次测试进程，用户原有实例保持运行。

# 截图插件内存核查（2026-11-02）

> 后续进展：同日已实施并验证内存优化，见[修复记录](../capture-memory-fix-20261102/README.md)。下文保留首次核查时的观察与结论范围；不再代表最终实现。

用户反馈插件卡片显示 179 MB。核查当前实际运行的截图插件及隔离实例，未修改生产代码，未重启用户进程。

## 统计口径与当前实例

`src/app/PluginSettings.cpp::memoryText` 显示 `WorkingSetSize`，包括共享和私有驻留页面；不是私有提交或峰值。[Windows 计数器定义](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2) 及 [工作集说明](https://learn.microsoft.com/en-us/windows/win32/procthread/process-working-set)。

读取当前用户实例时，工作集曾为 7.6 MB、私有提交 243.4 MB；后一次采样为工作集 20.0 MB、私有工作集 11.6 MB、私有提交 231.5 MB。用户仍可操作，两个时间点不能作为完全静止条件下的前后对照。

## 独立启动验证

使用同一已安装插件及 Qt 运行时，临时配置关闭所有截图热键和 PrtScn 接管，走生产 initialize 协议，不打开操作窗口、不触碰用户数据。见 [采样](measurements.json)：

| 状态 | 总工作集 MB | 私有工作集 MB | 私有提交 MB |
| --- | ---: | ---: | ---: |
| 启动后 2 秒，未截图 | 101.40 | 44.86 | 136.75 |
| 启动后 8 秒，未截图 | 101.40 | 44.86 | 136.75 |
| 启动后 25 秒，未截图 | 2.93 | 1.25 | 136.77 |

`IdleTrim` 已有闲置工作集回收；工作集下降不意味着已释放所有私有提交。生产启动路径会预建 WGC 设备、显示器 capture item 和全屏 Qt 遮罩，避免首次截图的初始化延迟。上述数字尚未逐项分配到各资源，不能将全部私有提交都归因于一个缓存。

## 普通截图驱动缓存假设

观察到长截图结束已有 ClearState/Flush/Trim，而普通 Grabber 没有，因此复制当前 `Grabber.cpp` 做临时变体，在普通截图关闭全部帧池后主动清理。探针编译同一生产 Grabber/Hdr 源码，设置 Per-monitor v2 DPI，与实际应用相同；只在内存中捕获、校验尺寸并释放，不保存屏幕图像，不发送输入。

每个进程连续 6 次捕获均实际走 WGC，见 [原实现](baseline-results.txt)、[清理变体](trim-results.txt)、[汇总](grabber-summary.json)。最后一轮释放图片后的私有提交为 67.57 / 66.31 MB，后五轮截图耗时中位数为 18 / 21 ms。这组试验没有显示足够的稳定内存收益，变体未加入生产代码。它仅覆盖抓帧器，不覆盖标注、OCR、录屏或完整 UI 使用循环；六轮稳定不能证明不存在任何长期泄漏。

临时探针和独立插件实例均已退出，用户原有 Win顺和截图插件保持运行。复现源码及脚本留在忽略目录 `build/capture-memory-20261102/`。

## 结论范围

179 MB 是某一时刻的总工作集，非持续独占的物理内存；已有闲置回收生效。私有提交在未截图时约 137 MB、用户使用后约 232–243 MB，仍值得进一步细分资源生命周期。此次没有确认需要修复的泄漏，也没有以改变卡片统计口径、强制退出插件或缩短回收间隔制造优化结果。

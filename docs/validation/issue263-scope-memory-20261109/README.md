# #263：重启后保持上次的搜索范围

2026-11-09，Windows 11 25H2、Qt 6.12.0、MSVC 2022 x64 Release，构建目录 `build/issues-249-253-256-20261108`（沿用前几轮的目录）。

**状态：代码写好，启动器这一层和真实 App 启动这一层都有自动测试并通过。没有在真实界面上用鼠标点过标签。** 没验证的部分见“没有验证的”。

## 做成什么样（这几条是我定的，可以推翻）

- 记住的是**用户自己选的**范围：点搜索框或面板上的标签、按 Tab、点类型胶囊或“内容”里的文件夹胶囊。存在 `state.ini` 的 `Search/Scope`（`all` / `files` / `content`；“文件夹”算在“文件”下，是哪一个由原有的 `Search/FileType` 决定）。没有加设置项。
- **路过的范围不记**：输入 `:pictures` 这类前缀时临时进的“文件”、插件结果行或插件命令设的范围、点“也搜内容”提示、“在此文件夹里搜索内容”、浏览进某个文件夹。理由：如果记“最后显示的范围”，用一次“在此文件夹里搜索内容”，以后每次启动都停在“内容”，一打字就去读文件内容，直到用户注意到标签；按现在的规则，最坏只是间接进入的范围没被记住。
- 开着「每次打开时清空搜索」时不恢复：这个设置的说明本来就是“回到全部”。
- “内容”也会恢复。内容搜索被关掉时回到“全部”；“合并文件范围”开着、又没选类型时，“文件”回到“全部”（那时标签里没有“文件”）。

## 改动

- `Launcher`：`scope` 属性的写入口从 `setScope` 改成新的 `chooseScope`（先 `setScope` 再记下）；Tab（`cycleScope`）、类型胶囊（`chooseFileType`、`toggleFileType`）、文件夹胶囊进“内容”也记。程序内部照旧调 `setScope`，不记。新增 `restoreScope`：只赋值并通知，不搜索，第一次显示时照常搜索。QML 没有改。
- `App::startRuntime`：恢复类型条之后调 `restoreScope`，开着「每次打开时清空搜索」时不调。
- `Preview.cpp`：两个检查（见下）；`tests/CMakeLists.txt`：四个测试。

## 测试

**启动器这一层**（`--preview-results <目录> --scope-memory`，`tst_scopememory`）：真的 `Launcher`、空索引、本次运行自己的 `state.ini`；一次“启动”就是按 App 的顺序新建并设置一个 `Launcher`。检查每个标签选了能记住并回来、Tab 和胶囊同样、内部设的范围和输入的前缀不被记下、“文件夹”随类型条一起回来、两种回退、启动时读类型条不会写下范围。本目录 `launcher/`：

| 构建 | 失败数 | 是哪些 |
|---|---|---|
| 真实代码（`real-code.json`） | 0 | — |
| 把“记下”关掉（`recording-disabled.json`） | 15 | 7 条“没被记住”全部失败，其余是连带的 |
| 把“恢复”关掉（`restoring-disabled.json`） | 6 | 正好是 6 条“没有回来” |

两个“关掉”的版本是在 `rememberScope` / `restoreScope` 开头临时加一行 `return` 构建的，跑完即还原（按保存副本的 SHA-256 核对）。

**App 这一层**（`--probe-runtime <目录> --scope-restore-check <files|content> [--clear-on-open]`，`tst_scoperestore_*`）：先往临时配置的 `state.ini` 写入范围，再真的 `App::start`（独立配置、HKCU 重定向、窗口在屏幕外），从窗口拿到的 `launcher` 上读范围。本目录 `app/`：

| 写入 | 清空搜索 | 启动后的范围 |
|---|---|---|
| `files` | 关 | 1（文件） |
| `content` | 关 | 2（内容） |
| `files` | 开 | 0（全部），此时 `state.ini` 里仍是 `files` |

第一行和第三行写入相同、只差那次调用有没有发生，所以这一对同时说明起作用的是那次调用。没有另外构建一个“删掉这次调用”的版本。

`ctest -R tst_scope`：4 个全过（11:10）。测试用的程序是 11:08:53 构建的；之后源码只加了 `Preview.h` 里 8 行注释和测试登记，当前源码另外构建通过（11:13）。构建编的是整个工作区，里面还有另一轮未提交的改动（Logo 右键等），与范围无关但确实在这个程序里。

## 顺带发现（不是这次改的，也没有改）

输入 `:pictures` 这类前缀时，`Launcher` 会发出“类型条的选择变了”的通知，App 收到就写进 `Search/FileType`；前缀删掉时再写回原来的。**如果前缀还在输入框里时程序退出**，`Search/FileType` 会停在前缀的类型上，下次进“文件”就是那个类型。以前要等用户自己进“文件”才看得到；现在范围会恢复，记住的范围是“文件”的用户一启动就会看到。测试里记录了这一点（三个 `launcher/*.json` 里的 `file_type_kept_while_prefix_typed` 都是 `pictures`）：看到的是 `Launcher` 发出的通知，写文件用的是测试里照着 App 写的处理，不是 App 自己那段。

## 上面这个前缀问题，后来修了（同一天下午）

- **改法**：前缀还在输入框里时，记下来的类型仍是前缀出现之前用户自己的选择（`Launcher::fileChoice` 有前缀时返回前缀之前那一份），类型条照旧显示前缀的类型。前缀还在时用户点了标签或类型，前缀被替换掉，这一刻才把类型条上的类型当成用户自己的记下（`clearQueryPrefix` 发通知），所以记下的和看到的一致。
- **顺带补上上午漏的一处**：前缀还在时点的正好是前缀显示的那个类型，原来连范围也不记，现在记成“文件”。
- **对照**：`--scope-memory` 里“前缀还在时记下的类型”，上午三个 json 都是 `pictures`；改后断言它是空（用户原来的“不限”），通过。新增两条：前缀还在时点同一个类型、点标签，记下的都和类型条一致，通过。结果见 `launcher/prefix-fixed.json`。
- **前缀原有的回归检查也跑了**：`--file-metadata` 里那一段（`:pictures 报告`、删掉前缀恢复原范围、多类型前缀、手动选类型替换前缀），没有失败。它没有登记成 ctest，是手动跑的。
- **没有验证的**：新加的两条没有看到过失败，是读代码判断的（去掉那次通知、或去掉记范围，各有一条会失败）。同样没有在真实界面上试。

## 过程中出过的错（影响怎么读结果）

- 还原“关掉”的版本时，是把保存的副本复制回去，复制保留了副本较早的修改时间，比用“关掉”版本编出的目标文件还早，构建工具认为不用重编。于是一次本应通过的运行用的还是“恢复被关掉”的目标文件，失败得和那个版本一模一样。给源文件换成当前时间（内容按哈希核对不变）后重编，构建步骤里出现 `Launcher.cpp.obj`，测试通过。之后每次重新链接的构建都核对了重编的是哪些文件（只改测试登记的那一次核对的是程序没有被重新链接）。
- 暂存时本文件涉及的四个源文件里都有另一轮未提交的改动。只暂存了本次的改动：按已提交版本的行号把本次的每一处放回去，并核对暂存之外剩下的正好是另一轮的那 13 行 + `Preview.cpp` 的 49 行。
